### 动态分表（ShardingSphere）设计说明（picture-backend）

本项目在 `picture-backend` 中对 **`picture` 图片表**做了**按空间维度的动态分表（同库分表）**设计，目标是解决图片数据量增长与团队空间热点带来的性能与运维问题。

---

### 为什么需要分库分表（结合业务场景）

`picture` 是图片主数据表，属于典型的“**高增长 + 高频读写**”表：上传、列表、搜索、协同编辑等核心路径都围绕它。

同时它有天然的“租户/空间”边界：`picture.spaceId`（为空表示公共图库），因此非常适合用空间维度进行拆分：

- **大表问题**：单表数据持续增长会导致索引膨胀、查询/分页变慢、备份恢复与 DDL 变慢。
- **热点租户问题**：少数大团队空间（尤其高等级空间）会产生大量写入与查询，拖慢整个单表。
- **隔离与路由优势**：绝大多数空间内操作天然带 `spaceId` 过滤条件，按 `spaceId` 分表可实现**精准路由到单表**，避免跨表广播。

> 现阶段落地的是 **同库分表**（先解决大表与热点隔离）。如未来需要扩容，也可以沿用同一分片键进一步扩展到**分库**（多数据源 + db 分片策略）。

---

### 分片键（Sharding Key）如何设计：为什么选 `spaceId`

本项目对 `picture` 表的分片键是 **`spaceId`**，原因：

- **最常用过滤条件**：空间相册列表、空间内搜索、空间协同编辑、空间权限校验等场景都以 `spaceId` 为入口。
- **天然租户边界**：空间是权限与配额（`Space.totalCount/totalSize`）的统计边界，用它拆分能将“同一空间的数据”聚合在一起。
- **稳定且高基数**：`spaceId` 不会像分类/标签那样频繁变化，避免数据迁移；空间数量大，有利于分布更均衡。

### 具体实现（项目真实代码）

#### 1) ShardingSphere 配置（按 `spaceId` 分表 + 自定义算法）

配置位置：`picture-backend/src/main/resources/application.yml`

- **逻辑表**：`picture`
- **分片列（Sharding Key）**：`spaceId`
- **分片算法**：`CLASS_BASED`，实现类为 `com.yupi.yupicturebackend.manager.sharding.PictureShardingAlgorithm`
- **actual-data-nodes**：初始配置为 `yu_picture.picture`，随后由运行时动态更新为 `yu_picture.picture, yu_picture.picture_{spaceId}, ...`

#### 2) 分表路由规则：`picture` -> `picture_{spaceId}`

实现类：`picture-backend/src/main/java/com/yupi/yupicturebackend/manager/sharding/PictureShardingAlgorithm.java`

路由规则要点：

- 当 `spaceId == null`：回到主表 `picture`（公共图库/非空间场景兜底）。
- 当 `spaceId != null`：优先路由到 `picture_{spaceId}`；如果目标表不存在，回退到主表 `picture`（避免未建表导致报错）。

#### 3) 动态建表与动态刷新分表节点（actual-data-nodes）

实现类：`picture-backend/src/main/java/com/yupi/yupicturebackend/manager/sharding/DynamicShardingManager.java`

核心机制：

- **建表**：`CREATE TABLE picture_{spaceId} LIKE picture`（保证表结构/索引一致）
- **动态刷新规则**：通过 ShardingSphere `ContextManager` 修改规则配置并 `reloadDatabase`
- **触发时机**：创建空间时尝试创建分表（见 `SpaceServiceImpl.addSpace`）
- **策略控制**：仅对“团队空间 + 旗舰版”建表，避免给小空间制造大量小表

> 注意：`DynamicShardingManager` 当前在代码中存在 `//@Component` 注释；`SpaceServiceImpl` 也写了“为方便部署，注释掉分表”的说明。这通常意味着：分表能力保留，但在特定部署环境（如单机演示/简化部署）默认关闭。

### 主要挑战与解决方案

#### 挑战 1：分表是动态的，ShardingSphere 默认偏静态配置

- **问题**：空间不断新增，如果不刷新 `actual-data-nodes`，新建的 `picture_{spaceId}` 不会被路由命中。
- **解决**：通过 `DynamicShardingManager.updateShardingTableNodes()` 运行时更新规则并 reload。

#### 挑战 2：跨分片查询（不带 `spaceId`）的代价

- **问题**：如果所有数据都拆到 `picture_{spaceId}`，全站/公共查询会变成跨 N 表广播，成本高。
- **解决（本项目策略）**：保留主表 `picture` 承载公共图库/兜底查询；空间内场景尽量强制携带 `spaceId` 做精准路由。

#### 挑战 3：范围路由（RangeSharding）未实现

- **现状**：`PictureShardingAlgorithm` 的 `RangeSharding` 返回空集合，意味着 `spaceId BETWEEN ...` 等范围条件无法正确路由。
- **解决思路**：
  - 业务侧尽量保持 `spaceId = ?` 的精确等值路由（空间内查询本就应该精确命中一个空间）。
  - 若确有范围扫描需求（如离线迁移/统计），补齐 Range 路由（返回可能表集合）或改为离线任务扫描。

#### 挑战 4：分表后的主键全局唯一

- **问题**：分表后不能依赖每表自增保证全局唯一，否则跨表引用/日志追踪会困难。
- **解决（项目现状）**：实体 `Picture` 使用 MyBatis-Plus `IdType.ASSIGN_ID` 生成分布式全局 ID，天然适配分表。

### 精炼版

- **为什么分库分表**：图片表是最大热点表，且请求天然按空间聚合；分表能隔离头部空间、控制大表膨胀、提升空间内查询与运维效率。
- **Sharding Key 怎么选**：选 `spaceId`，因为它是稳定的租户边界、最高频过滤条件，能让绝大多数请求单分片命中。
- **挑战怎么解决**：动态分表用“建表 LIKE + 动态刷新规则”；跨分片查询用“主表兜底 + 空间内强制带 spaceId”；SQL 形态优先精确等值路由（必要时补 Range）；ID 用全局分布式 ID。
