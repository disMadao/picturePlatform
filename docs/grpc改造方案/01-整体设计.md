# 01 - 整体设计

## 1. 改造目标

- **替换对象**：仅 **Agent → Java 内部调用**，当前通过 `JAVA_BASE_URL` + HTTP（如 `httpx`）访问的接口。
- **不替换对象**：浏览器 / 前端访问的 Spring MVC REST、用户登录、Sa-Token 主链路保持不变。
- **推荐策略**：**双栈并存**（同一时期 HTTP 与 gRPC 都可工作）→ 验证通过后，Agent 默认走 gRPC，HTTP 保留作回滚或运维。

## 2. 现状调用面（需覆盖）

与 `agent-backend` 中 `JavaBackendClient` 使用方式对应，至少包括：

| 能力 | 现有 HTTP 路径（示例） | 说明 |
|------|------------------------|------|
| 分页搜图 | `POST /picture/list/page/vo` | 文本条件分页 |
| 按 ID 取图 | `GET /picture/get/vo` | 详情 VO |
| Agent 视频落库 | `POST /video/agent/persist` | 长耗时，需大超时 |

鉴权现状：请求头 **`X-Internal-Token`**，与配置 **`AGENT_INTERNAL_TOKEN` / `agent.internalToken`** 一致；Java 侧 `AgentInternalAuthFilter` 在校验通过后会模拟管理员登录并处理 Sa-Token SPACE。

## 3. 目标拓扑

```
┌─────────────────┐     gRPC (HTTP/2)      ┌──────────────────────────┐
│  agent-backend  │ ─────────────────────► │  picture-backend        │
│  (Python)       │   Metadata: token      │  :8123 REST（对外不变）   │
│                 │                        │  :9090 gRPC（对内新增）   │
└─────────────────┘                        └──────────────────────────┘
```

- **REST**：继续占用现有端口（如 `8123`），对外服务。
- **gRPC**：建议 **独立端口**（如 `9090`），仅内网或本机访问；与 MVC 解耦，避免与 Servlet 过滤器链强耦合。

## 4. 契约层（Protobuf）

- 在仓库中固定目录存放 `.proto`（例如 `proto/picture_agent/v1/picture_agent.proto`）。
- **package** 带版本：`picture.agent.v1`，后续兼容演进可并列 `v2`。
- RPC 与 message 字段应与现有 DTO 对齐（如分页参数、`AgentVideoPersistRequest` 等），避免长期用「一整段 JSON 字符串」塞在 proto 里。

## 5. 鉴权设计（gRPC）

| HTTP 现状 | gRPC 对应 |
|-----------|-----------|
| `X-Internal-Token` 请求头 | **Metadata** 键，如 `x-internal-token`（ASCII） |
| `agent.internalToken` 比对 | **ServerInterceptor** 中读取 Metadata 与配置比对 |
| Filter 注入 Session / Sa-Token | gRPC **无 HttpSession**：需在拦截器或 `Context` 中注入「当前用户=管理员」，**业务 Service** 若依赖 `getLoginUser()`，需统一改为可从「内部调用上下文」解析用户（这是 Java 侧主要设计点之一） |

可选增强：内网 **mTLS**（双向 TLS），与 Metadata token 叠加，符合「零信任」内网调用习惯。

## 6. 错误与超时

- **超时**：现有 `persist_agent_video` 使用较长 HTTP 超时（如 600s），gRPC 侧应对 `stub` 调用设置相同量级的 **deadline**。
- **错误**：将业务错误映射为 `io.grpc.Status`（如 `INVALID_ARGUMENT`、`INTERNAL`），或在响应 message 中携带与现有 `BaseResponse.code` 一致的结构，便于 Python 侧统一处理。

## 7. 风险与缓解

| 风险 | 缓解 |
|------|------|
| Service 层强依赖 Session | 抽象「当前用户」来源；内部 gRPC 固定为配置的管理员用户 |
| 双份鉴权逻辑（Controller 与 gRPC） | gRPC 实现直接调 **Service**，Controller 可薄封装或阶段性保留 |
| 运维只熟悉 HTTP | 文档说明端口、健康检查；可对 gRPC 做 TCP 探测或反射（仅内网） |

## 8. 实施顺序建议

1. 定稿 **proto** 与生成脚本（Java / Python）。
2. **Java**：引入 gRPC Server、Interceptor、ServiceImpl 委托现有 Bean。
3. **Python**：生成 stub，新建客户端封装，用开关切换 HTTP/gRPC。
4. 联调、对照结果，再默认 gRPC。
